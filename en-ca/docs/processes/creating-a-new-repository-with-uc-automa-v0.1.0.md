# Process: Creating a New Repository with uc-automa

Version: 0.1.0
Status: Draft

## Purpose

This process creates a repository that follows uc-automa from its very first commit, rather than one that has to be migrated to it later. The repository is born with its identity and its reason for existing, then receives everything shared from uc-automa by subscription. Nothing shared is copied by hand.

It applies to any repository type. OSAT manager repositories follow the more detailed guide in uc-automa <a id="cite-steel-2026a"></a>[(Steel, 2026a)](#ref-steel-2026a), which adds stages for the managed tool. The examples here use `eleventy-website-vishpala-com`, a website repository. Replace it with your repository's name throughout.

## Steps

### Choose the name

The repository name becomes the `repository` value in `.uc-automa.yaml` and names the SAT sidecar, `.<repository>.assets/`. It may use only lowercase letters, digits and single hyphens. A domain name is written with hyphens, so `vishpala.com` becomes `vishpala-com`.

Gate: the name matches `^[a-z0-9]+(-[a-z0-9]+)*$`.

### Confirm a layout fits

Every repository names a layout type, which says what it may hold at the top level and where. The root is closed: `uc-automa check` reports any top-level path the layout does not describe, and there are no per-repository exceptions <a id="cite-steel-2026b"></a>[(Steel, 2026b)](#ref-steel-2026b).

List what the repository will hold, then compare it with the layouts under `conf/layouts/` in uc-automa at the version you will pin. In uc-automa 0.1.0 these are `base`, `python-tool`, `uc-automa` and `osat-manager`. If none describes the repository, the missing layout is a change to uc-automa, with its own decision record and release, made before `init` is run. The first commit does not depend on it, so the next three steps can go ahead meanwhile.

Gate: a layout exists that describes every top-level path the repository will hold, or work to add one is under way in uc-automa.

### Install uc-automa

uc-automa is a Python package. Its source under `lib/uc_automa/` is never run or copied directly; installing it provides the `uc-automa` command. Install it into a virtual environment in the new repository, together with uc-portage, which it depends on and which is not on a package index:

```sh
mkdir eleventy-website-vishpala-com
cd eleventy-website-vishpala-com
python3 -m venv .venv
PYYAML_FORCE_LIBYAML=0 .venv/bin/python -m pip install --no-binary pyyaml \
    "git+https://github.com/steelcj/uc-portage@v0.1.0" \
    "git+https://github.com/steelcj/uc-automa@v0.1.0"
.venv/bin/uc-automa --version
```

Activate the environment with `. .venv/bin/activate` to put `uc-automa` on your `PATH`. The installed version is the one `init` pins, and every later command requires the two to match, so everyone working in the repository installs the same tag. When the layout you need is not yet released, install uc-automa from a checkout of the branch that adds it instead, and pin the release once it is tagged.

Gate: `uc-automa --version` prints the version you mean to pin.

### Create the repository and its sidecar

Create the local repository fresh, with no files generated by a forge. Creating it on a forge and pushing are separate decisions, taken later.

```sh
git init -b main
uuidgen -r
mkdir .eleventy-website-vishpala-com.assets
```

Write the two sidecar files. Both names end in `.yaml`; the layout names them exactly, and the layout check reports `dc.yml` or `archive.yml` as missing.

`.eleventy-website-vishpala-com.assets/archive.yaml` identifies the repository as a SAT archive, using the UUID from `uuidgen -r`:

```yaml
sat:role: "archive"
dc:identifier: "urn:uuid:<the UUID>"
dc:title: "eleventy-website-vishpala-com"
dc:language: "en-CA"
dc:rights: "CC-BY-4.0"
```

`.eleventy-website-vishpala-com.assets/dc.yaml` holds the repository-wide Dublin Core defaults at the top of the metadata cascade. `uc-automa docs index` reads the creator and rights from it.

```yaml
dc:creator: "Christopher Steel"
dc:publisher: "Vishpala"
dc:rights: "CC-BY-4.0"
dc:language: "en-CA"
dc:format: "text/markdown"
```

`dc.yaml` does not repeat any document's front matter. Each document carries its own title, subject, date and identifier.

Gate: both sidecar files exist with these names.

### Record the founding decision

The founding decision is the repository's first decision record, numbered 0001. It says why the repository exists and the choices it is built on, so that the repository is born with its reason attached and every later decision can build on it. Draft it from uc-automa's decision template, `en-ca/templates/decision.md`, with a fresh identifier from `uuidgen -r`.

Name it `en-ca/docs/decisions/0001--<slug>-v0.1.0.md`. The slug starts with `build-` and names what the repository builds, as in `0001--build-manage-restic-v0.1.0.md`. Keep the technology out of the slug and in the content, so that a later change of stack does not make the name wrong. For the website the record is `0001--build-website-vishpala-com-v0.1.0.md`.

What the record covers depends on the repository's type. For a website, it records the purpose, the stack, the languages, the content structure, its relationship to any repository it replaces, and the licensing: code, documentation and content, plus anything excluded, such as logos and wordmarks, and anything under its own licence, such as fonts.

Gate: the decision record follows the template and its `dc:identifier` is a fresh UUID.

### Make the first commit

The first commit holds the sidecar and the founding decision, and nothing else. Stage those paths by name, so that `.venv/` and any files already in the directory stay out:

```sh
git add .eleventy-website-vishpala-com.assets en-ca/docs/decisions
git status
git commit -m "Initial commit: sidecar and founding decision"
```

Read `git status` before committing. Under "Changes to be committed" it lists exactly `archive.yaml`, `dc.yaml` and the decision record.

Gate: `git show --stat HEAD` lists the two sidecar files and the decision record, and nothing else.

### Initialise and receive the offerings

Once the layout is available in the installed uc-automa, write `.uc-automa.yaml`. `init` writes it once, with the name, the layout, the installed version as the pin, `en-ca`, and the offerings the layout requires; the repository owns the file from then on.

```sh
uc-automa init --repository eleventy-website-vishpala-com --layout <layout>
uc-automa offerings plan
uc-automa offerings apply
```

The offerings bring in `LICENSE` and `LICENSES/`, `REUSE.toml`, `CHANGELOG.md`, `VERSION`, the uc-automa signpost block in `CLAUDE.md`, `.gitattributes` and `.editorconfig`. Files the layout marks `from_offering` are changed in uc-automa, not in the repository.

`REUSE.toml` is the exception: it is planted once and is the repository's own record afterwards. The starting copy covers the usual paths of a Python tool. Add an annotation for each path it does not cover, such as a site's `src/` and `themes/`, and record there any licences beyond MIT and CC BY 4.0, such as a font's OFL, with its text in `LICENSES/` under its SPDX identifier.

Gate: `uc-automa offerings plan` reports nothing to do.

### Write the repository's own files

Write the files the layout requires that no offering provides. In the base layout these are `README.md`, `ROADMAP.md`, `CONTRIBUTING.md` and `.gitignore`. Ignore `.venv/` and anything a build produces, such as `node_modules/` and `_site/` for a website.

Only the listed uppercase files may use capitals, so other documents go under `en-ca/docs/`. A setup guide, for example, becomes `en-ca/docs/guides/setup/setup-v0.1.0.md` rather than `SETUP.md`.

Then add the repository's own content, generate the documentation index and check the whole repository:

```sh
uc-automa docs index
uc-automa check
```

Fix each finding the check reports. Each finding names the directive it enforces, and the directive explains the rule.

Gate: `uc-automa check` reports that the repository conforms.

### Commit the repository

```sh
git add -A
git status
git commit -m "Receive uc-automa offerings and add the repository's files"
```

Read `git status` before committing, to confirm that nothing ignored or generated has been staged. From here on, run `uc-automa check` before every commit, and `uc-automa offerings plan` to see whether shared files have drifted. Creating the repository on a forge, pushing and the first release are separate decisions.

Gate: the working tree is clean and `uc-automa check` passes.

## Principles

- The repository conforms from its first commit; nothing is migrated afterwards.
- Shared files arrive by subscription and are changed at their source.
- A missing layout is fixed in uc-automa, never worked around in the repository.
- The founding decision is written before the code, so the reasons are never reconstructed later.
