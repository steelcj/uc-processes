# Process: From Question to Practice

Version: 0.1.0
Status: Draft

## Purpose

This process helps people make choices, and later revisit them, without losing track of why they were made. It keeps people in charge: tools can suggest, warn and help, but a person decides. Rules come last, not first. A rule is only worth writing once a choice has been made, tried and found to repeat.

## Steps

### Ask the question plainly

Say what is being chosen, what it should achieve and what you need from the answer. This is often a sentence or two. A question that is hard to state plainly is usually not ready to be answered.

### Look at where you are

Record how things are done today, with a date, and be honest about it. This is a record, not a judgement, so describe what happens rather than what should happen. Once written, the snapshot is never rewritten. When things change, a new dated snapshot is added beside it.

### Evaluate the options

This is the radar's job. Each option is weighed against the Universal Cake Evaluation Metrics <a id="cite-steel-2026b"></a>[(Steel, 2026b)](#ref-steel-2026b), following the [uc-radar evaluation lifecycle](https://github.com/steelcj/uc-radar/blob/main/en/docs/radar/uc-radar--evaluation-lifecycle-v0-1-0.md) <a id="cite-steel-2026a"></a>[(Steel, 2026a)](#ref-steel-2026a). Pay particular attention to agency. Can people leave? Can they move their work elsewhere? Does it run on older systems and over low bandwidth?

The outcome is a ring and the reasons for it, not a decision. An evaluation informs the person who decides; it does not decide for them.

### A person decides

Christopher Steel decides, or a client decides for their own systems. The decision record says what was chosen and links to the evaluation behind it. It also says what would cause the decision to be reconsidered, and how to undo it. If a choice cannot be undone, the record says so before the choice is made, so that nobody makes it by accident.

### Try it in one place

Put the choice into real use in one repository or one site before going further. Real use finds what the evaluation missed. If it goes badly, only one place has to be put back.

### Make it easy, only once proven

When the same choice keeps coming up and has worked where it was tried, offer help so that people do not have to start from nothing each time. Help can be a template, an offering or a check.

A check explains and warns. A person can override it by stating a reason, and the override is recorded rather than blocked. The record of overrides is how a check learns where it is wrong.

### Revisit on purpose

Add new dated snapshots from time to time, so the record keeps up with how things are actually done. Reopen a decision when its reconsider condition comes true, not only when someone happens to notice. When a decision is replaced, mark it superseded and keep it, so the reasons behind past choices stay readable.

## Principles

- Every rule traces back to a decision a person made, and through that decision to an evaluation.
- History is added to, never edited.
- The process scales down. A small choice can go from question to decision in one paragraph.
- Nothing becomes mandatory just because it was automated.
